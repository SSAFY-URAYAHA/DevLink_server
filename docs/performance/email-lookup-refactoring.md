# 이메일 소문자 통일과 기존 색인 활용

작성일은 2026-11-06이며, 이번 구현의 기준 커밋은 `73b4bc8`이다. 범위는 웹 로그인·회원가입과 서버의 이메일 저장·조회다.

## 1. 현재 결론과 증거의 범위

이메일을 소문자로 저장하는 기존 규칙을 유지하면서, DB 조회의 불필요한 대문자 변환을 제거했다. 웹 입력값과 HTTP 요청값도 소문자로 통일했다. 기존 `users.email`의 UNIQUE 색인 `uk_users_email`을 활용할 수 있는 조건으로 조회한다.

| 구분 | 확보한 내용 | 해석 범위 |
| --- | --- | --- |
| 이번 코드 확인 | 서버에서 소문자 변환 후 일반 동등 비교, 웹에서 입력·전송 시 소문자 변환 | 구현 내용과 호출 구조를 확인한 결과 |
| 이전 로컬 실측 | 가상 회원 200,001명에서 기존 조회의 전체 탐색 확인 | 실제 운영 사용자 수나 운영 장애가 아님 |
| 이전 대안 실험 | 기존 대문자 조회에 표현식 색인을 추가하면 탐색량·조회 시간이 감소 | 이번 일반 동등 비교 구현의 측정값으로 사용할 수 없음 |
| 이번 변경의 성능 | 아직 미측정 | 개선율·실행 계획·로그인 응답 시간 확정 불가 |
| 프론트 입력 동작 | React 상태와 전송 코드 정적 확인 | 실제 브라우저·자동완성·키보드 검증은 미수행 |
| 기존 DB 데이터 | 정리용 마이그레이션 작성 | 실제 서비스 DB 조회·마이그레이션 실행은 미수행 |

사용자 지침에 따라 이번 작업에서 빌드·테스트·DB 실험을 실행하지 않았다. 문서의 과거 실측과 계산값은 아래에서 구분한다. 과거 실험의 원본 로그·임시 DB는 보관되지 않아, 포트폴리오 최종 증거로 사용하려면 이번 구현의 원본 결과를 다시 확보해야 한다.

## 2. 문제를 발견한 과정

### 사용자 기능은 정상인데 점검한 이유

로그인은 이메일로 회원 한 명을 찾은 뒤 비밀번호를 확인하는 기능이다. 회원이 적으면 회원 전체를 읽어도 응답이 빨라, 기능 확인만으로는 조회 비용 증가를 알아채기 어렵다. 회원 수가 늘어난 조건에서 기존 색인이 실제로 사용되는지 확인하기 위해 격리된 로컬 DB에 가상 회원을 준비했다.

이전 조사에서는 Java 21과 PostgreSQL 16.15 환경에서 기존에 컴파일된 실제 서버를 실행했다. 실제 회원가입 API로 생성한 로그인용 계정 1명에 가상 회원 200,000명을 추가했다. 측정용 비밀번호는 실험 전용 값이었다.

Hibernate가 DB에 전달하는 SQL에서 다음 검색 조건을 확인했다.

```sql
WHERE upper(email) = upper(?)
```

원인은 `UserRepository.findByEmailIgnoreCase()`였다. 회원가입 중복 검사에도 같은 방식의 `existsByEmailIgnoreCase()`가 사용되고 있었다. Spring Data JPA의 `IgnoreCase`는 대문자로 변환해 비교하는 조건을 생성한다. [Spring Data JPA 3.5 공식 문서](https://docs.spring.io/spring-data/jpa/reference/3.5/jpa/query-methods.html)

기존 DB에는 `UNIQUE(email)`로 생성된 색인이 있었다. 그런데 검색 조건은 `email` 자체가 아니라 `upper(email)`이었다. 이전 실행 계획에서 `Gather → Parallel Seq Scan`을 관측했다. 여러 DB 작업자가 회원 목록을 나눠 읽으며 대문자로 바꾼 이메일을 비교한 것이다.

### 쉬운 예시

저장된 이메일이 `alice@example.com`이면 기존 색인도 그 값을 기준으로 회원의 위치를 찾는다. 그런데 조회는 저장된 값들을 `ALICE@EXAMPLE.COM` 같은 형태로 바꾼 후 비교하도록 요청했다. 이미 소문자 저장 규칙이 있으므로, 입력값도 소문자로 바꾸고 `email = ?`로 비교하면 같은 규칙의 색인을 활용할 수 있다.

색인이 존재한다는 사실만으로 조회가 빨라지는 것은 아니다. DB가 실제 검색 조건에 그 색인을 활용할 수 있어야 한다. 실행 계획은 데이터 수·분포·통계·설정에 따라 달라지므로, 작은 테이블의 전체 탐색 자체를 실패로 판단하지 않는다. [PostgreSQL 실행 계획 공식 문서](https://www.postgresql.org/docs/16/using-explain.html)

## 3. 선택한 해결 방법과 이유

| 검토 방법 | 특성 | 판단 |
| --- | --- | --- |
| 소문자 저장·입력 유지 + 일반 동등 조회 | 기존 규칙과 기존 UNIQUE 색인 재사용 | 이번에 적용 |
| `upper(email)` 표현식 색인 추가 | 기존 대문자 비교 SQL을 유지하면서 검색 조건에 맞는 색인 추가 | 이전 실험에서 효과 확인. 현재 저장 규칙과 비교하면 추가 색인 유지가 필요 |
| 대소문자를 구분하지 않는 별도 DB 타입 도입 | DB 타입·확장 구성과 관련 동작 변경 필요 | 이번 범위에서는 기존 규칙으로 해결 가능 |

표현식 색인은 유효한 대안이지만, 추가 저장 공간과 쓰기 시 유지 비용이 필요하다. 이미 소문자 저장을 사용하고 있으므로 조회를 그 규칙에 맞추는 방법을 선택했다. 추가 색인의 실제 용량·쓰기 비용은 측정하지 않았다. [PostgreSQL 표현식 색인 공식 문서](https://www.postgresql.org/docs/16/indexes-expressional.html)

현재 서비스는 이메일 전체를 소문자로 다루는 계정 정책을 이미 사용한다. 이번 변경도 그 정책을 유지한다. 모든 이메일 시스템에서 대소문자를 동일하게 취급한다는 일반 규칙을 주장하는 것은 아니다.

## 4. 구현 내용

### 웹 입력과 요청

로그인과 회원가입은 `AuthPanel.tsx`의 이메일 입력창을 공유한다.

```tsx
onChange={(event) => setEmail(event.currentTarget.value.toLowerCase())}
```

- CapsLock·Shift·붙여넣기로 들어온 값도 변경 이벤트에서 소문자로 변환
- 화면에만 소문자로 표시하는 CSS 대신 실제 React 상태값 변환
- `autoCapitalize="none"`, `spellCheck={false}`로 입력 보조 설정
- 인증 API 함수에서도 `input.email.trim().toLowerCase()` 적용
- 입력 이벤트만으로 처리되지 않는 상황에도 전송 단계에서 소문자 규칙 적용
- 이름·닉네임·비밀번호에는 이메일 변환을 적용하지 않음

브라우저·비밀번호 관리 도구의 자동완성 이벤트 차이는 실제 확인이 필요하다. 일반적인 변경 이벤트와 API 전송 경로는 코드상 소문자 처리가 적용된다. 프론트 요청 시 대문자를 막는 것만으로 DB 조회 문제가 해결되지는 않는다. 서버 조회에서도 `IgnoreCase`를 제거해야 한다.

### 서버 조회

기존 `normalizeEmail()`은 그대로 사용한다.

```java
return email.strip().toLowerCase(Locale.ROOT);
```

| 기능 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 로그인 회원 조회 | `findByEmailIgnoreCase(normalizeEmail(...))` | `findByEmail(normalizeEmail(...))` |
| 회원가입 중복 검사 | `existsByEmailIgnoreCase(email)` | `existsByEmail(email)` |
| 저장 이메일 | 앞뒤 공백 제거·소문자 변환 | 동일 |
| 동시 회원가입 중복 방지 | `uk_users_email`과 기존 예외 처리 | 동일 |

로그인 검색 조건은 `upper(email) = upper(?)`에서 `email = ?`로 변경된다. 회원가입 중복 검사도 일반 동등 비교 조건으로 바뀐다. 실제 SELECT 형태와 LIMIT 표현은 Spring Data JPA·Hibernate가 생성하므로 SQL 로그에서 확인해야 한다.

프론트와 서버에서 각각 변환하는 목적은 다르다. 프론트는 사용자가 보고 입력하는 값과 전송값을 일치시키고, 서버는 어떤 요청 경로에서도 계정 식별 규칙을 보장한다. 일반 HTTP 요청으로 프론트를 거치지 않아도 서버 규칙이 유지된다.

### 기존 데이터 전환

이전 사용자 생성 코드는 소문자를 저장하지만 DB 자체에는 소문자만 허용하는 제약이 없었다. 수동 입력이나 과거 저장 경로로 대문자 이메일이 남아 있다면 일반 동등 조회 전환 후 로그인이 실패할 수 있다.

이를 보완하기 위해 `V11__normalize_user_emails.sql`을 추가했다.

1. 데이터 정리 중 회원 INSERT·UPDATE·DELETE가 끼어들지 않도록 테이블 쓰기 잠금 획득
2. `lower(email)` 기준 중복 계정 검사
3. 중복이 있으면 이메일 원문을 노출하지 않는 오류로 마이그레이션 중단
4. 대문자 이메일이 있는 행만 소문자로 갱신

계정을 자동으로 삭제·병합하지 않는다. 기존 UNIQUE 색인은 값 갱신에 따라 자동 유지된다. 새로운 색인이나 기존 V1 변경은 없다. PostgreSQL의 UNIQUE 제약은 고유 색인을 생성한다. [PostgreSQL 제약 조건 공식 문서](https://www.postgresql.org/docs/16/ddl-constraints.html)

Flyway의 PostgreSQL 기본 트랜잭션 실행을 전제로 실패 시 전체 정리가 롤백된다. [Flyway 트랜잭션 공식 문서](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/migration-transaction-handling)

테이블 쓰기 잠금은 마이그레이션 동안 다른 회원 쓰기를 대기시킬 수 있으므로 배포 시점을 고려해야 한다. 데이터 정리 자체의 소요 시간은 미측정이다. Java와 DB의 대소문자 변환이 달라질 수 있는 비ASCII 이메일 정책은 별도 확인이 필요하며, 아래 재현 데이터는 ASCII 이메일이다. [PostgreSQL 잠금 공식 문서](https://www.postgresql.org/docs/16/explicit-locking.html)

## 5. 이전 실험에서 확보한 측정값

아래는 이번 변경 이전에 수행했던 별도 대안 실험이다. SQL 조건을 그대로 유지하고 `upper(email)` 색인을 추가한 결과이며, 이번 `email = ?` 구현의 실측 결과가 아니다.

### 실험 조건

- PostgreSQL 16.15의 격리 Docker DB, Java 21
- 실제 서버 로그인 API와 가상 회원 총 200,001명 사용
- 같은 JVM·데이터에서 A 원래 상태 → B 표현식 색인 추가 → A2 색인 제거 순서
- 조건별 로그인 워밍업 12회, 순차 로그인 성공 요청 80회 측정
- CSRF 조회는 HTTP 로그인 측정 시간에 포함하지 않음
- 조건별 EXPLAIN ANALYZE 8회 중 첫 1회 제외, SQL 시간 중앙값 기록
- 모든 조건에서 Hibernate SQL DEBUG 설정 유지
- 캐시에 올라온 데이터 조건이며 공유 버퍼의 디스크 읽기 블록 수는 0
- 실험 기록 기준 커밋은 `b4553eb`. 현재 구현 기준 커밋과 다름

| 지표 | A 기존 조회 | B 대문자 표현식 색인 추가 | A2 색인 제거 |
| --- | ---: | ---: | ---: |
| 실행 계획 | Parallel Seq Scan | Index Scan | Parallel Seq Scan |
| SQL 실행 시간 중앙값 | 22.498ms | 0.034ms | 20.860ms |
| 공유 버퍼 hit 블록 수 | 3,178 | 4 | 3,178 |
| 공유 버퍼 read 블록 수 | 0 | 0 | 0 |
| 로그인 HTTP p50 | 91.251ms | 69.353ms | 87.543ms |
| 로그인 HTTP p95 | 108.683ms | 81.147ms | 96.959ms |

p95는 측정한 요청 중 약 95%가 그 시간 안에 끝났다는 의미다. 단일 배치 80회의 p95이므로 큰 표본이나 장기간 통계와 같은 안정성을 가진다고 해석하지 않는다. SQL 시간과 HTTP 시간은 별도로 측정했으므로 두 중앙값·분위수를 직접 빼서 다른 단계의 시간을 확정할 수 없다.

기록을 기계적으로 확인할 수 있도록 수치와 출처 한계를 `email-lookup-prior-observations.json`에 옮겼다. 이 JSON은 이전 실행 로그의 원본이 아니라 대화 기록을 전사한 자료다.

### 위 관측값으로 계산한 변화량

| 계산 지표 | 식 | 결과 |
| --- | --- | ---: |
| SQL 중앙값 감소량 | 22.498 − 0.034 | 22.464ms |
| SQL 중앙값 감소율 | (1 − 0.034 / 22.498) × 100 | 약 99.85% |
| SQL 중앙값 비율 | 22.498 / 0.034 | 약 661.7배 |
| 공유 버퍼 hit 감소율 | (1 − 4 / 3,178) × 100 | 약 99.87% |
| 최초 기준 로그인 p95 감소량 | 108.683 − 81.147 | 27.536ms |
| 최초 기준 로그인 p95 감소율 | (1 − 81.147 / 108.683) × 100 | 약 25.34% |
| 역전 기준 로그인 p95 감소율 | (1 − 81.147 / 96.959) × 100 | 약 16.31% |

공유 버퍼 hit는 메모리에 있는 DB 블록을 사용한 횟수다. 디스크 읽기 횟수·고유 블록 개수·서버 전체 메모리 사용량과 동일하지 않다. 계획 트리의 부모·자식 수치를 중복 합산하지 않는다.

SQL 구간의 개선이 로그인 전체의 같은 비율 개선을 의미하지 않는다. 로그인에는 비밀번호 해시 검증, 세션 처리, HTTP 왕복 등도 포함된다. 역전 비교에서도 기존 조건의 수치가 달라졌으므로 대표 수치 하나로 모든 환경의 개선율을 보장하지 않는다.

## 6. 이번 구현에서 확정 가능한 변화와 추정의 구분

### 코드로 확인한 변화

- 로그인·회원가입 조회의 `IgnoreCase` 메서드 2개 제거
- DB 검색 조건에서 이메일 열의 대문자 변환 제거
- 추가 영구 색인 0개, 기존 UNIQUE 색인 재사용
- 로그인·회원가입의 성공 경로에서 필요한 DB 조회 횟수는 기존과 동일
- 웹 공통 입력창 1곳으로 로그인·회원가입 모두 소문자 입력 처리
- 프론트 API 전송 경로 2곳에 소문자 변환 적용
- 기존 데이터 정리를 위한 마이그레이션 1개 추가

조회 횟수를 줄이는 변경이 아니라 같은 조회를 더 적은 탐색으로 처리할 수 있게 한 변경이다. DB가 실제로 `uk_users_email`의 Index Scan 등을 선택했는지는 이번 구현 실행 계획에서 확인해야 한다.

### 설명용 계산과 예상

전체 탐색은 회원 수가 늘면 확인할 이메일도 늘어난다. 색인은 정렬된 검색 구조를 이용해 목표 이메일의 위치를 찾으므로, 한 명을 찾기 위해 회원 전체를 확인하는 비용을 피할 수 있다. 정확한 색인 탐색 단계·블록 수·응답 시간은 데이터와 DB 상태에 따라 달라진다.

예를 들어 이전 별도 실험의 SQL 차이 22.464ms를 동일하게 반복된다고 가정하면, 1,000번 조회의 SQL 실행 시간 단순 합은 22.464초 차이다. 이는 관측값을 곱한 설명용 계산이며 실제 경과 시간·CPU 시간·서버 처리량·이번 구현의 성과가 아니다. 동시 요청의 응답 시간을 이 값으로 계산할 수 없다.

이번 구현에서도 전체 탐색 대신 기존 색인을 활용하고 조회 비용이 감소할 것으로 예상한다. 다만 표현식 색인과 기존 이메일 색인은 구조·분포가 다를 수 있어 이전 실험의 0.034ms나 25.34%를 이번 구현의 결과로 옮길 수 없다. 서버 전체 RPS·CPU·메모리 개선율은 현재 근거가 없다.

## 7. 배포 전 데이터 확인 방법

아래 SQL은 수동 확인용이며 이번 작업에서는 실행하지 않았다. 결과에는 이메일 원문을 포함하지 않는다.

```sql
SELECT
    count(*) AS user_count,
    count(*) FILTER (WHERE email <> lower(email)) AS mixed_case_user_count
FROM users;

SELECT count(*) AS case_insensitive_duplicate_groups
FROM (
    SELECT lower(email)
    FROM users
    GROUP BY lower(email)
    HAVING count(*) > 1
) AS duplicate_groups;
```

중복이 있으면 V11이 중단된다. 해당 계정들의 소유 관계를 확인하고 정리 방침을 정한 뒤 배포해야 한다. 실제 DB에 접속하지 않아 현재 계정 수와 중복 여부는 알 수 없다.

## 8. 이번 구현의 원본 증거를 확보할 절차

아래는 후속 실행 계획이며 현재 완료 결과가 아니다. 빌드·테스트 실행이 허용된 시점에 수행한다.

### SQL 조회 비교

`email-lookup-reproduction.sql`은 현재 세션의 임시 테이블에 `users` 구조와 기존 색인을 복제하고, 가상 회원 200,001명을 생성한다. 실제 사용자 테이블에는 INSERT·UPDATE·DELETE하지 않는다. SQL 조회 확인용 비밀번호 문자열이므로 HTTP 로그인 실험에는 사용할 수 없다. 데이터 구조·문자열 길이가 이전 실험과 완전히 같지 않아 같은 수치를 기대하면 안 된다.

이 스크립트는 검색 조건에 따른 색인 활용을 확인하는 용도다. 임시 테이블의 탐색은 병렬 실행이 제한되고 버퍼가 `local hit/read`로 기록되므로, 과거 일반 `users` 테이블의 Parallel Seq Scan·shared 블록 수와 직접 비교할 수 없다. 운영 형태의 계획과 수치를 확보하려면 격리 DB의 일반 테이블에서 실제 서버 SQL로 별도 측정한다. [PostgreSQL 병렬 실행 공식 문서](https://www.postgresql.org/docs/16/parallel-safety.html), [EXPLAIN 공식 문서](https://www.postgresql.org/docs/16/sql-explain.html)

```text
psql <격리된 로컬 DB 연결정보> -X -L email-lookup-plan.log -f docs/performance/email-lookup-reproduction.sql
```

- 새 psql 세션에서 실행하고 `--single-transaction`은 사용하지 않음
- 같은 임시 데이터에서 기존·변경 조회의 계획, Execution Time, Buffers 기록
- 로그인 성공 조회와 신규 이메일 중복 검사 각각 확인
- 각 조건 최소 8회 반복 후 첫 실행을 워밍업으로 분리
- A→B와 B→A 순서를 바꾸고 여러 라운드로 재확인
- 회원 1천·1만·20만 규모에서 같은 절차로 증가 경향 비교
- 통계 갱신, 데이터 분포, 병렬 설정, DB 버전, 표본 수 함께 저장
- 색인 강제 설정으로 결과를 유도하지 않고 DB의 실제 선택 확인
- 소규모에서 전체 탐색이 선택되더라도 대규모 결과와 구분해 해석

### 실제 API 비교

1. 격리 환경에서 변경 전·후 서버를 각각 실행
2. 실제 회원가입 API로 동일한 비밀번호 검증 조건의 실험 계정 생성
3. 같은 구조·개수의 가상 회원 준비
4. CSRF 준비 시간을 로그인 시간과 분리
5. 조건별 워밍업 12회 후 로그인 성공 요청 80회 이상 측정

## 9. 포트폴리오 작성 예시

### 현재 확보한 근거로 작성 가능한 문장

> 가상 회원 20만여 명을 이용한 로컬 조사에서, 이메일 색인이 있어도 로그인 조회가 회원 전체를 탐색하는 상황을 확인했다. SQL을 추적해 소문자로 저장한 이메일에 IgnoreCase 조회가 대문자 변환을 적용하는 점을 원인으로 파악했다. 웹 입력·API 전송·서버 조회를 소문자 기준으로 맞추고, 기존 UNIQUE 색인을 활용할 수 있도록 일반 동등 비교로 변경했다. 기존 계정의 조회 호환성을 위해 중복 확인과 소문자 정리 마이그레이션도 추가했다. 이번 변경의 성능 수치는 후속 측정으로 확인할 예정이다.

이전 대안 실험의 수치를 설명할 때는 다음과 같이 범위를 명시한다.

> 원인 검증용 별도 실험에서는 대문자 표현식 색인 추가 후 SQL 중앙값이 22.498ms에서 0.034ms로, 순차 로그인 80회의 p95가 108.683ms에서 81.147ms로 감소했다. 색인 제거 시 전체 탐색이 다시 나타났다. 최종 구현은 기존 소문자 저장 규칙과 색인을 재사용하는 방향을 선택했으며, 이 최종 구현의 개선율은 별도로 측정해야 한다.

### 최종 실측 이후 보완할 문장

> PostgreSQL [버전], 가상 회원 [수]명, [반복 조건]에서 기존 조회와 일반 동등 조회를 비교했다. 실행 계획이 [변경 전]에서 [변경 후]로 바뀌었고, SQL 중앙값 [전]ms→[후]ms, 로그인 p95 [전]ms→[후]ms를 관측했다. 추가 색인 없이 기존 `uk_users_email`을 재사용했으며, 대소문자 혼합 입력·중복 가입 동작을 확인했다.

괄호 안은 이번 구현의 실제 결과로 채운다. 운영 장애 해결, 운영 회원 수 20만 명, 모든 요청의 동일한 개선율, 확인하지 않은 자원 절감 수치는 기재하지 않는다.

## 10. 면접에서 설명할 핵심

- 왜 개선했는가 — 색인이 있는데도 회원 수가 증가하면 로그인 이메일 조회가 전체 회원을 읽는 상황을 가상 데이터로 발견
- 왜 기능 확인에서 드러나지 않았는가 — 정상 응답만 보면 검색 과정과 데이터 증가에 따른 비용이 보이지 않음
- 왜 프론트만 바꾸지 않았는가 — 프론트가 소문자를 보내도 서버의 IgnoreCase는 DB 열을 대문자로 변환
- 왜 새 색인을 추가하지 않았는가 — 이미 소문자 저장 정책과 UNIQUE 색인이 있어 조회 조건을 맞추는 편이 단순
- 동시 가입의 중복은 어떻게 막는가 — 기존 DB UNIQUE 제약과 기존 이메일 중복 예외 처리 유지
- 과거 계정은 어떻게 보호하는가 — 기존 데이터의 소문자 전환 전 중복 검사, 중복 시 자동 병합 없이 중단
- 무엇을 측정했고 무엇이 남았는가 — 과거 대안 실험의 실제 수치와 최종 구현의 미측정 상태를 구분
- 사용자 체감은 무엇인가 — 이메일 표기와 전송 규칙이 일치하며, 대규모 조회에서 로그인 대기 감소를 기대하되 실제 개선율은 후속 HTTP 측정으로 확인

## 11. 용어

| 용어 | 의미 |
| --- | --- |
| 정규화 | 같은 이메일을 서로 다르게 처리하지 않도록 공백 제거·소문자 변환 등 기준을 맞추는 것 |
| 색인·인덱스 | 필요한 데이터 위치를 빨리 찾도록 DB가 유지하는 검색 구조 |
| 동등 비교 | 두 값이 같은지 `=`로 비교하는 것 |
| 표현식 색인 | 원래 값 대신 `upper(email)`처럼 가공한 결과에 만든 색인 |
| 실행 계획 | DB가 어떤 순서와 방법으로 데이터를 찾을지 보여주는 정보 |
| Parallel Seq Scan | 여러 작업자가 테이블을 나눠 순서대로 읽는 방식 |
| Index Scan | 색인을 이용해 필요한 데이터 위치를 찾는 방식 |
| 공유 버퍼 hit | 필요한 DB 블록을 DB 메모리 캐시에서 사용한 횟수 |
| p50·중앙값 | 측정 요청 중 약 절반이 그 시간 안에 끝나는 지점 |
| p95 | 측정 요청 중 약 95%가 그 시간 안에 끝나는 지점 |
| 마이그레이션 | 배포 시 DB 구조나 기존 데이터를 정해진 순서로 변경하는 작업 |
