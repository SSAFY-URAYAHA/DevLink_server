- 담당: 중앙 실시간 연결·작업 알림
- 주요 작업: BROKER_READY 신원 정보 추가, 상태 변경·완료·거절 알림, PR #16의 Outbox 계약에 맞춘 발행·재시도 구현

## 1. 오늘 구현한 내용

### BROKER_READY에 인증된 사용자·팀 정보 추가

- 연결 준비 응답의 `payload`에 기존 `connection_id`, `agent_id`와 함께 `user_id`, `team_id`를 포함했다.
- 사용자·팀 ID는 클라이언트 입력이 아닌 인증된 `AgentPrincipal`에서 가져온다.
- `user_id`는 Agent 소유자의 ID이며, 토큰 원문·해시는 응답에 넣지 않는다.
- 재접속 후에도 브로커가 인증된 사용자·팀 정보를 다시 구성할 수 있도록 했다.

### 작업 상태 변경·완료·거절 알림

- 작업 수락·거절·실패는 `TASK_STATUS_CHANGED`, 완료 결과는 `TASK_COMPLETED`로 요청자 브로커에 전달한다.
- 기존 도메인의 `REJECTED`를 상태 변경 알림에 반영했다. 별도 거절 메시지 종류는 추가하지 않았다.
- 작업의 요청자 Agent가 원래 요청 사용자 소유이고 같은 팀인지 확인한다.
- 연결의 인증 Principal도 해당 Agent·사용자·팀과 일치해야 한다.
- 요청자 MCP가 OFFLINE이어도 현재 브로커 연결이 있으면 알림을 전송한다.
- 실제 쓰기 직전에 현재 연결을 재확인하고, 이전 연결의 전송 실패가 새 연결을 정리하지 않도록 했다.

### PR #16 Outbox 계약에 맞춘 전환

처음 구현한 메모리 이벤트·커밋 후 리스너 방식에서, PR #16이 제공하는 영속 Outbox를 읽는 방식으로 전환했다. 공통 Outbox 엔티티·마이그레이션·상태 변경 시 Outbox 저장은 PR #16의 구현을 재사용한다.

- 저장된 `message` JSON 전체를 그대로 전송한다. 재시도 시 현재 Task 상태로 메시지를 다시 만들지 않는다.
- `event_id`는 `outboxId`와 같은 UUID이며 재시도에도 유지한다.
- `task_id`, `version`은 최상위 JSON 숫자 필드로 맞췄다.
- `aggregate_type=TASK`, `destination=task-events`인 상태 변경·완료 알림만 처리한다.
- 메시지에 수신자 ID가 없으므로 작업 ID로 원래 요청자를 조회해 라우팅한다.
- 기존 `TaskNotificationEvent`, `TaskNotificationEventListener`, `TaskNotificationFailureRecorder`를 제거했다.
- 전송 실패는 Outbox의 상태·시도 횟수·`last_error`로 관리한다. 기존 Flyway 마이그레이션은 수정하지 않았다.

## 2. 최종 처리 흐름

```text
업무 트랜잭션
  작업 상태·결과·이력 저장
  → flush 후 갱신된 version 확보
  → Outbox JSON 저장
  → 함께 커밋

별도 발행기
  발행 가능한 PENDING 또는 점유가 만료된 PROCESSING 조회
  → 행 점유·시도 횟수 증가·커밋
  → 요청자와 현재 연결 검증
  → 소켓 쓰기 직전 점유 검증·연장·커밋
  → 저장된 JSON 전송
  → 성공: PUBLISHED / 실패: 재시도 예약 또는 FAILED
```

| Outbox 상태 | 의미 |
| --- | --- |
| `PENDING` | 최초 발행 또는 예약된 재시도를 기다리는 상태 |
| `PROCESSING` | 특정 발행기가 유효한 토큰으로 점유한 상태 |
| `PUBLISHED` | 서버의 WebSocket 소켓 쓰기가 성공한 상태 |
| `FAILED` | 최대 시도 횟수 초과 또는 잘못된 메시지로 자동 처리를 종료한 상태 |

**PUBLISHED는 브로커 수신 확인이 아니다.** 이번에는 소켓 쓰기 성공 기준을 선택했으며 알림 전용 ACK를 추가하지 않았다. 새 작업의 ACK·`deliveredAt` 처리와 기존 작업 라우팅의 `SENT` 처리도 변경하지 않았다.

### 중복 점유 방지·점유 만료 복구

- 짧은 트랜잭션에서 `FOR UPDATE SKIP LOCKED`로 다른 발행기가 잠근 행을 건너뛴다.
- 점유할 때마다 새 `lock_token`과 `locked_until`을 저장한다.
- 성공·실패 기록과 점유 연장은 자신의 토큰이 일치하고 점유가 유효한 경우에만 수행한다.
- 네트워크 전송 중에는 DB 트랜잭션·행 잠금을 유지하지 않는다.
- 서버 종료 등으로 남은 `PROCESSING`은 점유 만료 후 다시 처리한다. 이전 점유자가 새 점유자의 결과를 덮어쓰지 못하게 했다.
- PostgreSQL과 Java의 시각 비교를 마이크로초 정밀도로 맞춰 만료 경계 판단을 일치시켰다.

### 기본 설정

`application.yml`의 `devlink.outbox`에서 조정한다.

| 설정 | 기본값 |
| --- | --- |
| 자동 발행 | 활성화 |
| 배치 종료 후 다음 실행까지 간격 | 1초 |
| 배치당 최대 전송 처리 수 | 20개 |
| 점유 유효 기간 | 30초 |
| 최초 실패 후 대기 | 1초 |
| 재시도 대기 상한 | 60초 |
| 최초 시도 포함 최대 시도 횟수 | 5회 |

기본 실패 대기는 1초 → 2초 → 4초 → 8초이며 다섯 번째 실패는 `FAILED`로 종료한다. 오프라인도 시도 횟수에 포함한다. `FAILED`는 자동 재처리하지 않는다. 테스트 프로필에서는 자동 발행을 끄고 발행기를 명시적으로 호출한다.

## 3. 완료 API 담당자와의 연결점

`TaskCompletionOutboxWriter.enqueue(task)`를 추가했다. 완료 담당자는 권한·버전 검증 후 완료 상태·결과·변경 파일·업무 이력을 저장하는 **같은 트랜잭션**에서 이 메서드를 호출해야 한다.

```java
// 완료 상태·결과·변경 파일·업무 이력을 현재 트랜잭션에서 저장한 뒤 호출한다.
taskCompletionOutboxWriter.enqueue(task);
```

내부에서 flush 후 갱신된 버전으로 `TASK_COMPLETED` JSON을 만들고 Outbox에 저장한다. 현재 트랜잭션에서 관리하는 Task만 받으며, 트랜잭션 밖의 호출은 거부한다. 완료 저장이나 Outbox 저장·커밋이 실패하면 함께 롤백된다. 완료 API 자체는 별도 담당자의 연결이 남아 있다.

- 실제 PostgreSQL·WebSocket으로 요청자만 수신, 저장 JSON·ID 보존, 오프라인 재시도·최대 횟수 종료를 검증했다.
- 동시 발행기의 중복 점유 방지, 잠긴 행 건너뛰기, 점유 만료 복구·이전 토큰 차단을 검증했다.
- 전송 직전 점유 상실 시 미전송과 전송 성공 후 완료 기록 유실 시 동일 메시지 재전송을 검증했다.
- 완료 상태·결과·파일·Outbox의 함께 커밋·롤백, 새 작업용 ACK 대기 미등록을 확인했다.

전체 `./gradlew.bat build --no-daemon` 실행에서는 **394개 중 391개 통과**했다. 기존 브로커 연결 테스트 3개는 Tomcat 시작 중 `SocketException: Bad address: listen`으로 실패했으며, 해당 클래스만 단독 재실행해 **3개 모두 통과**했다. 전체 빌드가 한 번에 성공한 것으로 기록하지 않는다.

로컬 검증 프로세스에만 `-Djava.net.preferIPv4Stack=true -Dserver.address=127.0.0.1`을 적용했고, 실행 후 기존 환경값을 복구했다. 저장소의 JVM·네트워크 설정은 변경하지 않았다. 실제 Rust 브로커 대신 Java WebSocket 클라이언트와 테스트용 인증 Bean을 사용했다.

## 6. 남은 연동·전달 한계

- 완료 API 담당자가 같은 트랜잭션에서 `TaskCompletionOutboxWriter.enqueue(task)`를 호출해야 한다.
- 실제 브로커에서 알림 JSON을 수신하고 `event_id`로 중복을 제거해야 한다.
- 전송 성공 후 `PUBLISHED` 기록 전에 서버가 종료되면 중복 전송될 수 있다. `version`으로 오래된 알림이 최신 상태를 덮어쓰지 않게 해야 한다.
- 소켓 쓰기 성공 이후 브로커의 수신함 저장까지는 보장하지 않는다. 수신 확인이 필요하면 별도의 알림 ACK 계약이 필요하다.
- `FAILED`의 수동 재처리 정책은 후속 결정 사항이다. 발행 실패는 이미 커밋된 작업 상태·결과와 API 성공 응답에 영향을 주지 않는다.
