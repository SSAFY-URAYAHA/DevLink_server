# 2026-10-27 작업 기록 — 최보경

- 담당: 중앙 실시간 연결·라우팅
- 관련 업무: 브로커 연결 수신·인증 연동, Agent별 연결 등록·조회, 접속 상태 갱신
- 기준 구조: 사용자당 Agent 1개, 활성 브로커 1개
- 현재 범위: 서버 측 연결 수명과 Agent 접속 상태 처리 구현. 실제 브로커·인증 모듈 연동은 준비 후 확인 예정

## 1. 오늘 구현한 내용

### ConnectionRegistry

서버 메모리에서 `Agent ID → 현재 WebSocket 연결`을 관리하도록 구현했다.

- `register()`: 인증된 Agent의 열린 연결 등록
- `findByAgentId()`: 현재 열린 연결 조회. 닫힌 연결은 반환하지 않음
- `isCurrentConnection()`: 전달받은 세션이 현재 활성 연결인지 확인
- `unregister()`: 현재 등록된 실제 세션과 같은 경우에만 연결 제거
- 같은 Agent가 새로 연결하면 새 연결을 등록하고 기존 연결에 `4002` 종료 코드 전달
- 이전 연결의 지연 종료 이벤트가 새 연결을 삭제하지 않도록 세션 객체 비교
- 기존 연결 종료에 실패하더라도 이전 연결을 활성 연결로 복원하지 않음

### WebSocket 핸들러 연동 & BROKER_READY

- `/ws/broker` 연결 성공 시 `Authentication` 안의 인증된 `AgentPrincipal` 확인
- 클라이언트 입력 대신 인증된 Agent ID로 Registry 등록
- 등록된 현재 연결에만 `BROKER_READY` 전송
- 응답에 현재 `connection_id`와 숫자 `agent_id` 포함
- 연결 종료 시 해당 연결만 Registry에서 해제
- READY 전송 실패 시 등록 정보와 연결 정리. 정리 중 발생한 추가 오류는 원래 예외에 보관
- 코드의 인증 확인·연결 등록·교체·정리 흐름에 한국어 설명 주석 작성·정리

### AGENT_PRESENCE 수신 & DB 상태 갱신

`AgentPresenceService`를 추가하고 기존 Agent 엔티티의 상태 변경 기능을 재사용했다.

- 메시지를 보낸 세션의 인증 정보와 현재 연결 여부 확인
- 허용 상태: `ONLINE`, `OFFLINE`
- Agent ID는 메시지 본문이 아닌 인증된 연결에서 확인
- DB의 Agent 소유자·팀과 인증 정보가 일치하는지 추가 확인
- ONLINE 보고: `agents.status`와 서버 현재 시각의 `last_seen_at` 갱신
- OFFLINE 보고: 상태만 갱신하고 마지막 온라인 확인 시각 유지
- 같은 상태가 다시 보고돼도 오류 없이 처리
- 잘못된 JSON·필드·타입·상태와 JSON 뒤의 추가 값은 `1008`로 연결 종료
- AGENT_PRESENCE에는 별도 ACK를 보내지 않음

수신 메시지 형식:

```json
{
  "type": "AGENT_PRESENCE",
  "payload": {
    "status": "ONLINE"
  }
}
```

### 연결 종료 & 동시 상태 변경 보호

- 현재 연결이 실제로 해제됐을 때만 DB 오프라인 갱신 수행
- Agent별 DB 행 잠금으로 접속 보고와 종료 시 상태 변경을 직렬화
- 잠금을 기다리는 동안 연결이 교체될 수 있으므로 잠금 획득 후 현재 연결을 재확인
- 이전 연결의 지연 메시지·종료 처리가 새 연결의 접속 상태를 덮어쓰지 않도록 보호
- 이미 삭제된 Agent의 종료 정리는 오류 없이 처리

## 2. 구현한 전체 흐름

```text
브로커가 Agent 토큰으로 /ws/broker 연결 요청
    ↓
인증 필터 → AgentTokenVerifier 연동 → 인증된 AgentPrincipal 전달
    ↓
WebSocket 연결 성공 후 ConnectionRegistry 등록
    ↓
서버 → 브로커: BROKER_READY
    ↓
브로커 → 서버: AGENT_PRESENCE
    ↓
메시지 검증 → 현재 연결 확인 → AgentPresenceService
    ↓
DB의 status·last_seen_at 갱신
```

연결 종료 시에는 Registry에서 현재 세션을 해제하고, 새 활성 연결이 없는지 확인한 뒤 해당 Agent를 오프라인 처리한다.

## 3. 오늘 정리한 설계 기준

| 항목 | 기준 |
| --- | --- |
| Agent 정보·상태 저장 | DB의 agents 테이블 |
| 실제 WebSocket 연결 저장 | 서버 메모리의 ConnectionRegistry |
| BROKER_READY의 의미 | 서버와 브로커의 인증·연결 등록 완료 |
| AGENT_PRESENCE의 의미 | 로컬 Agent와 브로커 사이의 접속 상태 보고 |
| Agent 온라인 판정 | 토큰 검증 성공이나 READY 전송만으로 ONLINE 처리하지 않음 |
| AGENT_PRESENCE 전송 시점 | 최초 READY 수신 직후, Agent 상태 변경 시, 재접속 후 READY 수신 직후 |
| 서버 재시작 | 메모리 연결 정보는 사라지며 브로커 재접속으로 다시 구성 |
| 현재 연결 교체 | 동일 Agent의 최신 연결 유지, 이전 연결 종료 |
| 실제 전달 가능 여부 | DB 상태뿐 아니라 Registry의 현재 열린 연결도 함께 확인 필요 |

브로커의 실제 자동 재접속 동작은 클라이언트 담당 범위다. 서버에 새 연결을 등록하는 것과 사용자·Agent를 DB에 새로 등록하는 것은 다르다.

## 6. 남은 작업

- 인증 담당자의 실제 AgentTokenVerifier 구현 Bean 연동과 토큰 발급·폐기 정책 확인
- 클라이언트 담당자와 READY·PRESENCE JSON 형식을 맞추고 실제 브로커로 연동 확인
- 하트비트 구현 및 무응답 연결 정리. 논의한 초기안은 PING 20초 간격, PONG 대기 20초, 서버의 PING 무수신 판정 40초
- TASK_CREATED 라우팅, 수신함 기록 후 ACK 확인, 전달 결과 저장
- 작업 상태·결과 알림 구현과 최종 메시지 종류 합의
- 토큰 폐기·Agent 삭제·로그아웃 시 연결 종료 정책 연동

상세 통신 계약은 [브로커 연결 인증 계약](../../../bogyeong/docs/broker-authentication.md)을 참고한다.
