### 토큰 사용 구조 확인

- 웹에서 `POST /api/v1/agents/{agentId}/token`으로 토큰을 발급한다.
- 코드 대조상 서버는 해당 Agent의 `connection_token_hash`에 SHA-256 해시를 저장하고 원문을 발급 응답으로 반환한다.
- 프론트는 원문을 화면 메모리에만 보관하며, 토큰 창을 닫으면 지운다.
- 이번 수동 테스트에서는 복사한 B 토큰을 PowerShell의 `DEVLINK_TOKEN` 환경변수로 브로커에 전달했다.
- A·B의 Agent 전용 REST 호출에는 각 토큰을 `Authorization: Bearer ...` 헤더로 사용했다.
- `GET /api/v1/agent/context`에서 B의 `agentId=2`, `teamId=1`, `ownerUserId=2`를 확인했다.
- 중앙 Agent 토큰과 브로커가 별도로 발행하는 MCP용 `localToken`은 구분해서 사용했다.

## 4. 작업 생성·수신·ACK 검증

### 첫 번째 테스트: 작업 1

- `POST /api/v1/agent/tasks`로 A가 B에게 작업 요청
- 생성 응답에서 `success=true`, `taskId=1`, `status=PENDING`, `delivery.status=ACK_PENDING` 확인
- 상세 조회에서 `CREATED → ACK_PENDING → ACK_RECEIVED` 이력 확인
- ACK 기록 후 작업 버전은 `1`, 업무 상태는 `PENDING`
- 이 작업은 수신·ACK 확인까지만 수행했고 수락·완료 테스트에는 사용하지 않았다.

### develop 업데이트 후 테스트: 작업 2

- 명세에 있는 `POST /api/v1/tasks/{teamId}` 경로로 새 작업 생성
- 실제 요청 주소는 `POST /api/v1/tasks/1`, 요청자 A와 수신자 B 사용
- 상세 조회에서 `taskId=2`, `teamId=1`, 요청자 Agent 1, 수신자 Agent 2 확인
- 프롬프트: `최신 develop 작업 흐름 테스트입니다. 수락과 완료 등록까지 확인합니다.`

| 이벤트 | 서버 응답 시각 원문(시간대 표시 없음) |
| --- | --- |
| CREATED | 2026-10-30 04:52:10.945 |
| ACK_PENDING | 2026-10-30 04:52:11.002 |
| ACK_RECEIVED | 2026-10-30 04:52:12.487 |

전달 대기 기록 후 약 1.49초 만에 ACK가 기록됐다. 코드의 저장 후 ACK 경로와 실제 `ACK_RECEIVED` 이력을 근거로, 실제 B Rust 브로커의 수신·저장·ACK 처리까지 확인했다. 수신함 파일을 직접 열어 내용까지 대조한 결과는 제출되지 않았다.

ACK는 전달·수신 확인이며 작업 수락이나 실행 완료를 의미하지 않는다. 상세 응답에 `deliveredAt` 필드는 없어 ACK 확인은 `events`의 `ACK_RECEIVED`로 판단했다.

## 5. 작업 수락·완료·결과 조회 검증

### B의 작업 수락

- `PATCH /api/v1/tasks/2/status`
- B의 Agent 토큰으로 인증
- 요청 본문: `status=IN_PROGRESS`, `version=1`
- 응답: `success=true`, `status=IN_PROGRESS`, `version=2`
- `startedAt` 기록 및 `PENDING → IN_PROGRESS: 작업 수락` 이력 확인

### B의 완료 등록

- `POST /api/v1/tasks/2/complete`
- B의 Agent 토큰과 수락 후 버전 `2` 사용
- 결과 문장: `작업 흐름 테스트 완료. 수신과 수락을 확인했으며 실제 파일 수정은 없습니다.`
- `taskFiles=[]`로 실제 파일 변경 없이 결과 문장만 등록
- 응답: `success=true`, `status=COMPLETED`, `version=3`, `completedAt` 기록

### A의 최종 결과 조회

- `GET /api/v1/tasks/2`를 A의 Agent 토큰으로 조회
- 최종 상태 `COMPLETED`, 버전 `3`, 한글 `resultText` 정상 반환
- 시작·완료 시각 및 전체 상태 변경 이력 확인
- 변경 파일 목록은 빈 배열로 반환

| 단계 | 상태 | 버전 | 확인 내용 |
| --- | --- | ---: | --- |
| 생성·ACK 완료 후 | PENDING | 1 | CREATED·ACK_PENDING·ACK_RECEIVED |
| B 수락 후 | IN_PROGRESS | 2 | startedAt·수락 이력 |
| B 완료 후 | COMPLETED | 3 | resultText·completedAt·완료 이력 |

```text
A의 수동 작업 요청
→ 중앙 서버 저장
→ 실제 B Rust 브로커 수신·저장
→ ACK 전송·서버 이력 기록
→ B 토큰으로 수락 API 호출
→ B 토큰으로 완료 결과 등록
→ A 토큰으로 최종 결과 조회
```

작업 수락·완료는 PowerShell에서 API로 직접 요청했다. 실제 AI가 작업을 수행하거나 파일을 수정한 결과로 기록하지 않는다.

## 6. 작업 목록·상태 필터 검증

| 조회 | 사용한 조건 | 확인 결과 |
| --- | --- | --- |
| A가 보낸 목록 | `scope=mine&direction=sent&page=0&size=20` | 작업 2(COMPLETED), 작업 1(PENDING) |
| B가 받은 목록 | `scope=mine&direction=received&page=0&size=20` | 같은 두 작업 조회 |
| A의 완료 목록 | `scope=mine&direction=sent&status=COMPLETED` | 작업 2만 조회, 작업 1 제외 |

- API: `GET /api/v1/teams/1/tasks`
- 기본 두 목록 모두 `totalElements=2`, `totalPages=1`, `hasNext=false`
- 최신 생성 순서인 작업 `2 → 1`로 반환
- 완료 필터는 `totalElements=1`, 작업 2의 시작·완료 시각 정상 반환
- 두 작업 모두 A가 B에게 보낸 작업이므로 A의 보낸 목록과 B의 받은 목록이 같은 것은 정상
- 반대 방향의 빈 목록, 팀 전체 조회, 여러 페이지 이동은 이번에 검증하지 않음

## 7. 실행 중 확인한 문제와 대응

| 문제 | 대응·확인 결과 |
| --- | --- |
| cmd에서 `Invoke-RestMethod` 인식 실패 | PowerShell 사용 또는 `curl.exe`로 헬스체크 |
| PowerShell에서 `npm.ps1` 실행 차단 | 실행 정책을 바꾸지 않고 `npm.cmd install`, `npm.cmd run dev` 사용 |
| `cargo` 명령 인식 실패 | C++ 사전 도구 설치와 Rust 설치를 구분해 진행하고 새 PowerShell에서 빌드 |
| 브로커 기동 중 Windows 권한 검사 실패 | 테스트 폴더 소유자가 Administrators인 것을 확인하고 일반 PowerShell에서 재실행한 뒤 정상 기동 |
| 브로커가 `Reconnecting` 유지 | REST 헬스·Agent 인증 성공 확인 후 WebSocket 진단. 중앙 주소를 `127.0.0.1:8080/ws/broker`로 명시한 뒤 Connected 확인 |
| 별도 PowerShell WebSocket 진단의 헤더 오류 | `Connection: upgrade, keep-alive` 거부 관측. 이후 curl에서는 `101`, `Connection: upgrade` 확인. 이를 Rust 재연결의 확정 원인으로 기록하지 않음 |
| 세션 생성 후 다시 OFFLINE | 세션 만료 가능성을 고려해 20초 간격 자동 갱신 추가 후 ONLINE 확인 |
| 작업 요청의 `AUTHENTICATION_REQUIRED` | A 토큰을 다시 입력하고 요청 헤더를 재구성한 후 작업 생성 성공 |
| JSON의 한글 깨짐 | 원본 응답 바이트를 UTF-8로 읽었을 때 프롬프트·결과 문장 정상 확인. 응답 해석 문제로 구분 |
| 웹·CLI 로그인에서 `INVALID_CREDENTIALS` | CLI에서도 HTTP 401 확인. 사용자가 해결 후 로그인 성공을 보고했으며 최종 원인·해결 조치는 공유되지 않음 |

토큰 재입력 후 성공한 사실과 토큰 원문이 잘못됐던 정확한 원인은 구분한다. 로그인 문제도 쿠키·서버·사용자 입력 중 특정 원인으로 단정하지 않으며, 비밀번호 초기화를 수행했다고 기록하지 않는다.

## 8. 동작 확인 상태 정리

정상 흐름의 수동 검증 기준이다. 권한·오류·동시성 등 전체 수용 조건을 모두 검증했다는 의미는 아니다.

| 기능 | API | 오늘 확인한 범위 | 판정 |
| --- | --- | --- | --- |
| Agent 등록 | `POST /api/v1/agents/teams/{teamId}` | 웹에서 A·B Agent 등록 | 확인 |
| Agent 목록 | `GET /api/v1/agents/teams/{teamId}` | 목록 및 B ONLINE 표시 | 확인 |
| Agent 상세 | `GET /api/v1/agents/{agentId}` | 웹에서 이름을 클릭하는 방법 안내까지만 진행 | 결과 확인 대기 |
| Agent 수정 | `PATCH /api/v1/agents/{agentId}` | 직접 실행하지 않음 | 미검증 |
| Agent 삭제 | `DELETE /api/v1/agents/{agentId}` | 직접 실행하지 않음 | 미검증 |
| 연결 토큰 발급 | `POST /api/v1/agents/{agentId}/token` | 웹 발급 후 실제 인증·연결·요청에 사용 | 확인 |
| 작업 요청 | `POST /api/v1/tasks/{teamId}` | 작업 2 생성·전달·ACK | 확인 |
| 작업 목록 조회 | `GET /api/v1/teams/{teamId}/tasks` | A 보낸 목록·B 받은 목록·완료 필터 | 확인 |
| 작업 상세 조회 | `GET /api/v1/tasks/{taskId}` | 내용·상태·결과·이력 | 확인 |
| 작업 상태 변경 | `PATCH /api/v1/tasks/{taskId}/status` | PENDING에서 IN_PROGRESS 수락 | 확인 |
| 작업 완료 등록 | `POST /api/v1/tasks/{taskId}/complete` | 빈 파일 목록과 결과 문장 등록 | 확인 |

`GET /api/v1/agent/context`는 토큰으로 확인한 Agent 신원을 조회하는 별도 API다. 이 호출 성공을 `GET /api/v1/agents/{agentId}`의 상세 조회 검증으로 대체하지 않았다.
